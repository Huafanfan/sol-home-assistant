# ADR-0004：采用文档驱动的规格先行开发

## 状态

已接受（2026-08-16）

## 背景

Sol 同时涉及语音状态机、家庭隐私、长期记忆、第三方语音服务、持续运行和未来的真实世界工具。仅依靠代码或单次聊天上下文，无法让后续 session 稳定理解既有边界，也容易在功能迭代时悄然扩大权限、数据外发或成本范围。

项目需要让每个功能在编码前就具备可审阅的目标、非目标、模块边界、数据/权限、失败语义和验收标准，并能追溯其与架构决策的关系。

## 决策

- 将文档作为产品意图和约束的事实来源，代码作为实现；不要求文档逐行复述代码。
- 根目录 `AGENTS.md` 是未来 session 的执行门槛；`docs/START-HERE.md` 是当前项目状态和阅读路径的入口。
- T1 及以上变更先建立 `docs/features/<feature>.md`；T2/T3 还必须建立或更新 ADR。功能规格必须在实施前达到 `accepted`。
- 功能规格使用 `draft`、`accepted`、`implemented`、`verified`、`superseded` 生命周期，并回填实现路径、测试和真实运行证据。
- T1/T2 默认先有仅文档提交，再有实现提交；若用户明确要求压缩提交历史，仍不得在规格达到 `accepted` 前编辑实现。
- 每项事实只能有一个权威文档。功能规格链接架构、Provider、Deployment 与 ADR，而不是复制价格、接口或隐私规则。
- T0 的纯文案、格式和无行为变化重构不要求新规格；不确定时提高到 T1。涉及外部副作用或不可逆操作的 T3 必须有用户明确授权。

## 后果

后续 session 可以从仓库内的文档而非聊天记忆恢复项目上下文；设计、实现和验收之间也有明确的可追溯链路。对语音、记忆、部署和供应商边界的修改会在编码前暴露出来。

代价是每个有行为变化的功能都需要先写规格并维护验证证据。为避免文档负担失控，本决策限定 ADR 只用于跨模块或难逆转选择，并允许 T0 走轻量流程。

静态检查或 CI 将来可以检查“实现变更是否同时关联文档”，但不能自动判断语义是否正确；文档复核仍是每个 session 的必要步骤。
